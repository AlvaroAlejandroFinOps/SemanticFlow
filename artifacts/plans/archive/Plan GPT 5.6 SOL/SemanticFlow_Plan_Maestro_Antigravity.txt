======================================================================
0. PROPOSITO DE ESTE DOCUMENTO
======================================================================

Este documento es la instruccion maestra para evolucionar SemanticFlow desde un compilador local determinista orientado a Power BI y TMDL hacia una plataforma enterprise de Semantic Model Engineering, manteniendo Power BI como backend de referencia y preservando el funcionamiento actual.

El agente de Antigravity debe usar este documento como plan de ejecucion gradual. No debe interpretar este plan como autorizacion para implementar todas las fases de una sola vez. Cada fase requiere analisis, propuesta de impacto, implementacion pequena, pruebas, evidencia y cierre antes de avanzar.

Objetivos del plan:

1. Preservar la arquitectura desacoplada Parser -> AST -> Compiler -> Emitter.
2. Evitar regresiones en la generacion actual de PBIP y TMDL.
3. Introducir progresivamente un Canonical Semantic Model neutral respecto del proveedor.
4. Organizar la plataforma en capacidades de producto y vistas por persona.
5. Incorporar gobierno, seguridad, calidad, linaje, explicabilidad y operacion como capacidades de primera clase.
6. Consolidar Power BI como primer target enterprise.
7. Preparar, sin implementar todavia, una arquitectura extensible para futuros targets.
8. Posponer expresamente los emitters de Looker/LookML y Qlik Sense/Qlik Cloud para actualizaciones futuras.
9. Profesionalizar el repositorio para su publicacion en GitHub y su presentacion en empresas.
10. Mantener una experiencia local y offline como capacidad base, sin agregar dependencias cloud obligatorias.

1. CONTEXTO Y ESTADO ACTUAL QUE DEBE PRESERVARSE
======================================================================

SemanticFlow es actualmente un compilador local determinista de modelos semanticos para Power BI. Transforma esquemas relacionales en Markdown, YAML o JSON en proyectos PBIP y codigo TMDL.

Arquitectura actual confirmada:

- Parsers de entrada.
- AST relacional crudo basado en Pydantic v2.
- Semantic Compiler Engine.
- Inferencia de roles y relaciones.
- Reglas basicas de gobierno.
- Generacion de medidas DAX.
- TMDL Emitter.
- PBIP Writer.
- CLI basada en Typer y Rich.
- Pruebas unitarias, de integracion y stress.

Rutas actuales relevantes:

- src/cli.py
- src/core/ast/
- src/core/parsers/
- src/core/engine/compiler.py
- src/core/engine/
- src/core/emitter/
- tests/
- tests/Massive Stress Test/
- tests/Massive Data Stress/
- Artefactos/
- 001_Seed/
- pyproject.toml
- README.md

Restricciones inviolables iniciales:

- Mantener indentacion TMDL mediante tabuladores.
- Mantener el comportamiento determinista.
- No agregar dependencias cloud obligatorias al nucleo.
- No romper los parsers existentes.
- No romper los contratos publicos sin estrategia de compatibilidad.
- Mantener el ocultamiento automatico de claves foraneas como regla configurable de gobierno.
- No convertir TMDL ni DAX en el modelo canonico neutral.
- No implementar Looker ni Qlik durante este plan base.

2. VISION OBJETIVO
======================================================================

Vision en espanol:

SemanticFlow es un compilador abierto y determinista de modelos semanticos que transforma contratos declarativos de datos en modelos analiticos gobernados, comprobables, explicables y desplegables sobre plataformas empresariales de BI.

Vision tecnica:

SemanticFlow debe evolucionar hacia un framework declarativo y extensible capaz de:

- Descubrir y normalizar metadatos.
- Representar conceptos fisicos, analiticos y empresariales.
- Inferir semantica con evidencia y explicacion.
- Definir metricas gobernadas.
- Aplicar politicas de calidad y seguridad.
- Validar modelos antes de emitirlos.
- Compilar artefactos especificos por plataforma.
- Generar documentacion y linaje.
- Integrarse con CI/CD.
- Mantener trazabilidad completa desde fuente hasta artefacto generado.

Arquitectura objetivo conceptual:

Fuentes y contratos
    -> Parsers e Importers
    -> Raw Metadata AST
    -> Canonical Semantic Model
        -> Semantic Inference
        -> Metric Compiler
        -> Governance Policies
        -> Security Policies
        -> Quality Validation
        -> Optimization Rules
        -> Lineage Graph
    -> Target Capability Planner
    -> Target Adapters
        -> Power BI / TMDL / PBIP, implementacion de referencia
        -> Documentacion, implementacion temprana
        -> Looker / LookML, futuro
        -> Qlik Sense / Qlik Cloud, futuro
        -> Otros targets, futuro

3. MODELO ORGANIZATIVO DE DOS DIMENSIONES
======================================================================

El producto debe ordenarse mediante dos dimensiones complementarias. No se deben crear motores separados por profesion. Todas las personas deben consumir el mismo Canonical Semantic Model, usando vistas, validaciones, permisos, comandos o reportes adaptados a sus necesidades.

------------------------------------------------------------------
3.1 DIMENSION A: CAPACIDADES DEL PRODUCTO
------------------------------------------------------------------

A1. Descubrimiento e ingesta de metadatos

Responsabilidades:

- Leer Markdown, YAML y JSON existentes.
- Incorporar gradualmente SQL DDL como fuente declarativa.
- Detectar tablas, columnas, claves, relaciones y tipos.
- Registrar origen y evidencia de cada metadato.
- Diferenciar metadatos declarados, inferidos y enriquecidos.
- Permitir validacion previa antes de compilar.

A2. Modelado semantico

Responsabilidades:

- Representar tablas de hechos, dimensiones y puentes.
- Declarar grano.
- Modelar dimensiones conformadas.
- Modelar dimensiones de rol.
- Soportar copo de nieve de forma controlada.
- Representar jerarquias.
- Representar relaciones y su cardinalidad.
- Registrar ambiguedad y rutas de filtro.
- Distinguir semantica neutral de propiedades exclusivas de Power BI.

A3. Definicion de metricas

Responsabilidades:

- Definir metricas base, derivadas y KPI.
- Declarar expresion logica neutral cuando sea posible.
- Registrar implementacion DAX como expresion especifica del target.
- Declarar unidad, formato, moneda y periodicidad.
- Declarar aditividad, semi-aditividad o no aditividad.
- Registrar numerador y denominador para ratios.
- Declarar dimensiones compatibles y filtros predeterminados.
- Mantener dependencias entre metricas.
- Asignar ownership y estado de certificacion.

A4. Gobierno y seguridad

Responsabilidades:

- Propietario y data steward.
- Clasificacion de sensibilidad.
- Identificacion de PII y otros datos regulados.
- Row-Level Security.
- Object-Level Security.
- Enmascaramiento como capacidad neutral cuando corresponda.
- Retencion y restricciones de uso.
- Politicas obligatorias, advertencias y recomendaciones.
- Excepciones documentadas y auditables.

A5. Optimizacion

Responsabilidades:

- Analizar cardinalidad declarada o estimada.
- Detectar columnas innecesarias.
- Evaluar relaciones potencialmente costosas.
- Recomendar estrategias de particionamiento.
- Representar storage mode de forma neutral y mapearlo al target.
- Evaluar Import, DirectQuery, Direct Lake y modelos compuestos cuando el target sea Power BI.
- Separar escala de metadatos de escala de datos.
- Producir recomendaciones sin alterar automaticamente decisiones criticas.

A6. Validacion y pruebas

Responsabilidades:

- Validacion de contratos.
- Pruebas del modelo semantico.
- Pruebas de reglas de negocio.
- Pruebas de relaciones.
- Pruebas de metricas.
- Pruebas de seguridad.
- Pruebas de compatibilidad por target.
- Pruebas deterministas y de regresion.
- Golden files para emitters.
- Semantic Quality Score.

A7. Compilacion por plataforma

Responsabilidades:

- Mantener Power BI como target de referencia.
- Separar Canonical Semantic Model de la representacion Power BI.
- Introducir Target Capability Planner.
- Informar compatibilidad total, transformada, parcial, no soportada o pendiente de revision.
- Mantener emitters como adaptadores reemplazables.
- No implementar Looker ni Qlik en el alcance inicial.

A8. Documentacion y linaje

Responsabilidades:

- Diccionario de datos.
- Catalogo de metricas.
- Documentacion de entidades empresariales.
- Diagramas Mermaid.
- Linaje fuente -> tabla -> columna -> metrica -> KPI -> target.
- Analisis de impacto.
- Registro de decisiones de inferencia.
- Diferenciacion entre elementos declarados, inferidos y heredados.

A9. Despliegue y operacion

Responsabilidades:

- CLI estable.
- Salida humana mediante Rich.
- Salida estructurada JSON.
- Codigos de salida consistentes.
- Dry run.
- Validate-only.
- Explain.
- Diff semantico.
- Compilacion reproducible.
- Integracion con GitHub Actions.
- Versionado y changelog.
- Telemetria opcional y desactivada por defecto.

4. PRINCIPIOS ARQUITECTONICOS OBLIGATORIOS
======================================================================

P1. Vendor neutrality in the core

El nucleo no debe depender conceptualmente de Power BI. Los conceptos especificos de Power BI deben modelarse como extensiones o configuraciones del target.

P2. Power BI first, not Power BI only

Power BI seguira siendo la implementacion de referencia y el unico target BI completo durante este plan. La arquitectura debe quedar preparada para otros destinos, sin implementar integraciones prematuras.

P3. Declarative over imperative

Los contratos de entrada deben expresar intencion y semantica. La generacion de artefactos debe ser responsabilidad del compilador.

P4. Determinism

La misma entrada, configuracion y version del compilador deben producir la misma salida.

P5. Explainability

Cada inferencia relevante debe registrar regla, evidencia, confianza y resultado.

P6. Policy as Code

Las reglas de gobierno, seguridad y calidad deben ser configurables, versionables y comprobables.

P7. Compatibility before emission

Cada target debe declarar sus capacidades. El sistema debe detectar incompatibilidades antes de generar archivos.

P8. Backward compatibility

Los contratos actuales deben mantenerse o migrarse mediante adaptadores, versionado y mensajes claros.

P9. Offline-first

La compilacion base debe seguir funcionando localmente y sin servicios cloud.

P10. Small changes with evidence

No realizar refactorizaciones masivas sin checkpoints. Cada cambio debe venir acompañado por pruebas y evidencia.

5. MODELO DE EJECUCION OBLIGATORIO PARA EL AGENTE ANTIGRAVITY
======================================================================

Para cada fase y cada tarea, el agente debe seguir exactamente este ciclo:

PASO 1. Inspeccion

- Leer los archivos afectados.
- Confirmar el comportamiento actual.
- Identificar contratos publicos.
- Identificar pruebas existentes.
- Enumerar riesgos laterales.
- No escribir codigo todavia.

PASO 2. Plan de cambio

- Explicar objetivo.
- Enumerar archivos que se crearan o modificaran.
- Declarar supuestos.
- Definir criterios de aceptacion.
- Definir pruebas nuevas y pruebas de regresion.
- Confirmar que el cambio respeta las restricciones arquitectonicas.

PASO 3. Implementacion minima

- Implementar el incremento mas pequeno que entregue valor verificable.
- Evitar mezclar refactorizacion, funcionalidad y cambios cosmeticos en una sola tarea.
- Mantener tipado estricto.
- Agregar docstrings donde exista logica publica o no obvia.

PASO 4. Pruebas focalizadas

- Ejecutar primero pruebas del modulo afectado.
- Corregir errores antes de ampliar el alcance.
- No silenciar pruebas ni reducir aserciones para obtener resultados verdes.

PASO 5. Regresion completa

- Ejecutar la suite completa.
- Ejecutar stress tests relevantes.
- Verificar determinismo.
- Comparar golden files cuando corresponda.

PASO 6. Evidencia

- Informar comandos ejecutados.
- Informar resultados.
- Informar archivos modificados.
- Informar advertencias y deuda pendiente.
- Registrar decisiones arquitectonicas relevantes.

PASO 7. Gate de cierre

Una tarea solo puede marcarse completada si:

- Compila.
- Pasan las pruebas focalizadas.
- Pasa la regresion completa.
- Se cumplen criterios de aceptacion.
- Se actualiza documentacion relevante.
- No se introducen secretos.
- No se agregan dependencias cloud obligatorias.

Si una validacion falla, el agente debe detener el avance hacia la siguiente tarea, diagnosticar el problema y corregirlo dentro del alcance actual.

0.2 Ejecutar y documentar todas las pruebas existentes.
0.3 Registrar tiempos basales de compilacion para Tier 1, Tier 2 y Tier 3.

------------------------------------------------------------------
FASE 3. CANONICAL SEMANTIC MODEL MINIMO
------------------------------------------------------------------

Objetivo:

Introducir una representacion semantica neutral sin reemplazar de inmediato el AST actual.

Estrategia:

Aplicar patron Strangler. El AST actual sigue funcionando. Se introduce una capa canonica en paralelo y un mapper controlado.

Modelo canonico minimo sugerido:

- SemanticProject
- DataSource
- SemanticEntity
- SemanticAttribute
- SemanticRelationship
- SemanticMetric
- BusinessTerm
- GovernanceMetadata
- SecurityMetadata
- TargetExtension
- ProvenanceRecord
- Diagnostic

Propiedades transversales sugeridas:

- id estable.
- name tecnico.
- display_name.
- description.
- source_reference.
- declared_or_inferred.
- inference_evidence.
- owner.
- tags.
- annotations.
- target_extensions.

Tareas:

3.1 Diseñar contratos antes de escribir emitters nuevos.
3.2 Escribir ADR sobre la separacion entre core neutral y Power BI.
3.3 Implementar modelos Pydantic del canonico.
3.4 Implementar mapper Raw AST -> Canonical Model.
3.5 Implementar mapper Canonical Model -> representacion Power BI existente.
3.6 Mantener el pipeline antiguo disponible durante la transicion.
3.7 Crear comparacion de equivalencia entre pipeline antiguo y nuevo.
3.8 Agregar serializacion JSON determinista del canonico para inspeccion.

Criterios de aceptacion:

- El mismo input genera salida Power BI equivalente.
- El canonico no contiene tipos llamados DAX, TMDL o PBIP como requisitos centrales.
- Las propiedades especificas de Power BI viven en extensiones de target.
- Se preserva determinismo.

------------------------------------------------------------------

7. FUNCIONALIDAD FUTURA EXPRESAMENTE FUERA DEL ALCANCE ACTUAL
======================================================================

Las siguientes capacidades deben contemplarse en la arquitectura, pero NO deben implementarse durante las fases iniciales ni introducir dependencias prematuras.

------------------------------------------------------------------
7.1 LOOKER / LOOKML
------------------------------------------------------------------

Estado: FUTURO.

Decision:

Looker sera evaluado como segundo backend semantico una vez estabilizados:

- Canonical Semantic Model.
- SemanticMetric.
- Target Capability Planner.
- Plugin SDK.
- Matriz de compatibilidad.
- Power BI reference adapter.

Lineamientos futuros:

- Implementar Canonical Model -> LookML.
- Nunca implementar TMDL -> LookML como arquitectura principal.
- Evaluar views, dimensions, measures, dimension groups, explores y joins.
- Declarar diferencias de seguridad y comportamiento.
- Crear golden tests y ejemplos equivalentes.

No hacer ahora:

- No agregar dependencias de Looker.
- No crear emitter incompleto en produccion.
- No afirmar portabilidad completa.

------------------------------------------------------------------
7.2 QLIK SENSE / QLIK CLOUD
------------------------------------------------------------------

Estado: FUTURO POSTERIOR A LOOKER.

Decision:

Qlik requiere un adapter consciente de su paradigma asociativo. No debe tratarse como un dialecto de TMDL.

Lineamientos futuros:

- Evaluar load scripts.
- Master dimensions.
- Master measures.
- Calendarios.
- Deteccion de synthetic keys.
- Deteccion de referencias circulares.
- Associations.
- Section Access.
- Diferencias entre Qlik Sense, Qlik Cloud y escenarios legacy.

No hacer ahora:

- No traducir relaciones tabulares directamente sin analisis semantico.
- No agregar QlikView como target prioritario.
- No prometer equivalencia uno a uno.

------------------------------------------------------------------
7.3 OTROS HORIZONTES
------------------------------------------------------------------

Tambien quedan para evaluacion futura:

- dbt Semantic Layer o MetricFlow.
- MCP Server.
- Extension visual para IDE.
- API local opcional.
- Catalogo web.
- Integraciones con catalogos externos.
- Otros targets BI.

Estas ideas no deben retrasar la consolidacion del nucleo.

8. ESTRATEGIA DE PRUEBAS OBLIGATORIA
======================================================================

8.1 Piramide de pruebas

- Unitarias para contratos, reglas y mappers.
- Integracion para pipeline completo.
- Golden tests para emitters.
- End-to-end para CLI.
- Property-based tests para invariantes cuando sea apropiado.
- Regression tests para bugs corregidos.
- Stress tests para escala de metadatos.
- Performance tests con presupuestos claros.

8.2 Invariantes esenciales

- Determinismo.
- No perdida silenciosa de semantica.
- IDs estables.
- Orden estable de emision.
- Compatibilidad de entradas actuales.
- Diagnosticos reproducibles.
- No exposicion de secretos.
- Core independiente de targets.

8.3 Fixtures minimos

- Modelo estrella simple.
- Modelo copo de nieve.
- Dimension de rol.
- Tabla puente.
- Many-to-many.
- Calendario fiscal.
- Metricas dependientes.
- Seguridad RLS.
- Datos sensibles.
- Modelo ambiguo que debe fallar.
- Modelo grande sintetico de metadatos.

8.4 Regla de correccion

Cada bug corregido debe agregar una prueba que falle antes de la correccion y pase despues.

8.5 Regla de golden files

Los golden files no pueden actualizarse automaticamente para ocultar diferencias. Cada cambio esperado debe revisarse y justificarse.
