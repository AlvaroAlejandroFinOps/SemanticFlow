0. PURPOSE AND AUTHORITY OF THIS DOCUMENT
======================================================================

This document defines the architecture, functional scope, organizational model, implementation sequence, validation gates and acceptance criteria for evolving the current SemanticFlow persona views into a complete Persona Lens Framework.

Antigravity must analyze this specification and convert it into an incremental implementation plan before modifying code. It must not implement the complete framework in a single iteration.

The expected result is not a collection of static reports and not a set of unrelated filters. The expected result is a coherent organizational interpretation layer over the Canonical Semantic Model.

SemanticFlow must become capable of presenting one semantic truth through multiple purpose-specific lenses for analysts, engineers, architects, governance teams, domain owners, risk teams and data leaders.

A special Data Leadership Cockpit must be isolated in its own module and directory, while remaining fully connected to the Canonical Semantic Model, Persona Lens registry, quality engine, lineage, ownership, capability planner, diagnostics and organizational recommendation engine.

This document is normative for the Persona Lens initiative. If the repository conflicts with this document, Antigravity must identify the conflict, document it and propose the smallest safe migration. It must not silently rewrite existing contracts.

======================================================================
1. STRATEGIC PRODUCT DEFINITION
======================================================================

SemanticFlow must be positioned as:

An open and deterministic semantic engineering platform that transforms declarative data contracts into governed, testable, explainable and deployable analytical models, and projects the same semantic truth into role-specific decision views for the complete data organization.

Extended value proposition:

SemanticFlow does not only compile semantic models. It creates a shared, traceable and governed interpretation of the business. It adapts that interpretation to each data role and turns semantic metadata into technical artifacts, organizational responsibilities, quality controls, risk evidence, team interactions and leadership decisions.

SemanticFlow should provide three kinds of value simultaneously:

1. Semantic engineering value
   - Canonical modeling.
   - Metrics.
   - relationships.
   - governance.
   - target compilation.

2. Persona decision value
   - Tailored information.
   - role-specific diagnostics.
   - recommendations.
   - approvals and responsibilities.
   - relevant deliverables.

3. Organizational leadership value
   - Portfolio health.
   - ownership coverage.
   - capability gaps.
   - cross-team dependencies.
   - delivery flow.
   - operational and semantic risk.
   - investment priorities.

2. FOUNDATIONAL DEFINITIONS
======================================================================

2.1 Persona

A Persona is an organizational responsibility profile. It is not necessarily a job title, user account or individual person.

A small organization may assign several Personas to one person. A large organization may assign one Persona to a group, office or multiple teams.

Personas must therefore be:

- Composable.
- Configurable.
- Non-exclusive.
- Assignable to individuals, groups or teams.
- Independent from a fixed organization chart.
- Defined by responsibilities, decisions and expected outcomes.

2.2 Persona Lens

A Persona Lens is a deterministic projection of the Canonical Semantic Model that adapts content, technical depth, business context, risk interpretation, diagnostics, recommendations, responsibilities and deliverables to a specific Persona.

A Persona Lens is not:

- A duplicate semantic model.
- A separate source of truth.
- A hardcoded dashboard.
- An authorization system by itself.
- A copy of inference or quality logic.

A Persona Lens must never mutate the Canonical Semantic Model.

2.3 Persona Projection

A Persona Projection is the generated result of applying a Lens to a Canonical Semantic Project at a specific point in time.

A Projection must contain:

- Project identity.
- Persona identity.
- Compiler and schema version.
- Source build identifier.
- Relevant semantic objects.
- Summaries.
- Diagnostics.
- Recommendations.
- Responsibilities.
- Dependencies.
- Evidence references.
- Generation timestamp or deterministic build metadata policy.

2.4 Organizational Recommendation

An Organizational Recommendation is an explainable suggestion about role involvement, team interaction, missing ownership, capability gaps, approval needs or workflow improvements.

It must include:

- recommendation_id.
- rule_id.
- title.
- explanation.
- evidence.
- affected assets.
- affected Personas.
- recommended interaction mode.
- urgency.
- severity.
- expected outcome.
- blocking or advisory status.

2.5 Leadership Cockpit

The Data Leadership Cockpit is an aggregate decision module for Team Leads, Tech Leads, Engineering Managers, Heads of Data, Heads of Data and AI, Directors of Analytics, Directors of Data Platform and Chief Data Officers.

It must be isolated from individual Lens implementations, but consume their registered outputs and common services. It must never become a second semantic truth or duplicate core computation.

2.6 Team Interaction

A Team Interaction describes how two or more organizational units should work together for a bounded purpose.

Supported modes:

- COLLABORATION: joint work for a defined period to discover or create a new capability.
- X_AS_A_SERVICE: one team provides a stable capability consumed by another.
- FACILITATION: one team helps another overcome a capability gap.

2.7 Responsibility Assignment

A Responsibility Assignment connects a semantic activity or asset with organizational responsibility.

Recommended responsibility types:

- RESPONSIBLE.
- ACCOUNTABLE.
- CONSULTED.
- INFORMED.
- APPROVER.
- STEWARD.
- RISK_OWNER.
- TECHNICAL_OWNER.
- BUSINESS_OWNER.

4. ARCHITECTURAL PRINCIPLES
======================================================================

P1. One Canonical Semantic Truth

Every Lens and the Leadership Cockpit must derive from the same CanonicalSemanticProject.

P2. Read-only Projection

Persona Lenses must not mutate the Canonical Semantic Model. Recommendations and proposed changes must be separate artifacts.

P3. No Duplicated Domain Logic

Inference, quality scoring, lineage, target compatibility and governance rules remain in their core services. Lenses consume their results.

P4. Vendor Neutrality

All general Persona Lenses must be target-neutral. Target-specific information may be shown through explicit target extensions. BI Developer may consume Power BI-specific projections.

P5. Explainability

Every recommendation, alert and score must reference evidence and a rule.

P6. Configurability

Organizations must be able to rename, combine, deactivate and extend Personas without editing core logic.

P7. Privacy by Projection

Each Lens must expose only the minimum metadata needed for its purpose.

P8. Determinism

The same Canonical Project, configuration and compiler version must generate equivalent projections.

P9. Separation of Decision Support and Authorization

SemanticFlow may recommend roles and approval flows. It must not pretend to be a complete identity, HR or access-management platform.

P10. Leadership Aggregation without Recalculation

The Leadership Cockpit aggregates registered Lens results and core evidence. It must not recalculate independent quality, lineage or risk facts.

P11. Evidence before Maturity Claims

No Lens can be marked complete or enterprise-ready without tests, documented behavior, fixtures and measurable acceptance criteria.

P12. Incremental Migration

Preserve compatibility with current EXECUTIVE, DATA_GOVERNANCE and BI_ENGINEER views through adapters or deprecation paths.

7.1 DATA ANALYST LENS
------------------------------------------------------------------

Purpose:

Enable analysts to discover, understand and safely use trusted metrics and dimensions without interpreting physical schemas, surrogate keys or target serialization internals.

Primary decisions:

- Select the correct metric.
- Select compatible dimensions.
- Understand filters, units and time context.
- Decide whether a metric is certified and suitable.
- Identify whom to contact for clarification.

Questions answered:

- What metrics are available?
- What does each metric mean?
- Which metrics are certified?
- Which dimensions can be used with a metric?
- Which filters are implicit or recommended?
- What calendar and grain apply?
- When was the underlying information refreshed?
- Which warnings affect interpretation?
- Are two similarly named metrics equivalent?
- Who owns the definition?

Visible information:

- Business metric name and description.
- Certification status.
- Business owner and steward.
- Dimension compatibility.
- Units, currencies and formats.
- Time grain and calendar.
- Default filters.
- Business synonyms.
- Freshness status.
- Simplified lineage.
- Usage examples.
- Consumer warnings.

Hidden by default:

- Repository paths.
- TMDL properties.
- Surrogate keys.
- Internal compiler classes.
- Physical partitions.
- Sensitive implementation details.

Functional capabilities:

- Metric catalog.
- Business glossary search index.
- Certified metric filter.
- Dimension compatibility matrix.
- Similar metric comparison.
- Ambiguous naming warning.
- Missing description warning.
- Unit and currency conflict warning.
- Freshness indicator when metadata exists.
- Suggested owner contact.
- Consumer-friendly impact summary.

Recommendations:

- Request certification.
- Avoid incompatible metric-dimension combinations.
- Use an approved alternative metric.
- Clarify an ambiguous definition with Domain Owner.
- Escalate stale or incomplete metadata.

Inputs received from:

- Analytics Engineer.
- Domain Owner.
- Governance Officer.
- Data Engineer for freshness and availability.

Outputs delivered to:

- Business users.
- BI Developers.
- Domain Owners through feedback.

Default artifacts:

- ANALYST_METRICS_CATALOG.md
- BUSINESS_GLOSSARY.md
- CERTIFIED_METRICS.md
- DIMENSION_COMPATIBILITY.md
- ANALYST_WARNINGS.json

Minimum tests:

- Sensitive technical fields are excluded.
- Certified and draft metrics are correctly differentiated.
- Dimension compatibility is deterministic.
- Ownership is visible when defined.
- Missing descriptions generate actionable diagnostics.
- Projection does not mutate the canonical model.

Acceptance criteria:

An analyst can select and interpret a metric without reading DAX, TMDL or physical schema definitions.

9. TEAM ORCHESTRATION ENGINE
======================================================================

SemanticFlow may provide decision support for data-team orchestration. It must not become an HR management or autonomous staffing system.

9.1 Supported team topology classifications

- STREAM_ALIGNED.
- PLATFORM.
- ENABLING.
- COMPLICATED_SUBSYSTEM.

9.2 Suggested SemanticFlow mapping

Stream-aligned teams:

- Own domain data products and semantic assets.
- Include or access Domain Owner, Data Engineer, Analytics Engineer and analytical consumption capabilities.

Platform team:

- Operates SemanticFlow, CI/CD, templates, diagnostics, artifact delivery and self-service capabilities.

Enabling team:

- Helps domains adopt semantic modeling, governance, testing or analytics practices.

Complicated-subsystem team:

- Owns inference algorithms, compiler internals, complex optimization, advanced validation and target translation.

9.3 Interaction recommendation rules

Recommend COLLABORATION when:

- A new domain or metric family is being designed.
- Meaning is disputed.
- A new target capability is experimental.
- An interface or contract is not yet stable.

Recommend X_AS_A_SERVICE when:

- A platform capability is stable and documented.
- Inputs and outputs are contractual.
- Consumer teams should not need implementation expertise.

Recommend FACILITATION when:

- A domain repeatedly fails the same quality rules.
- A team lacks a temporary capability.
- Governance or testing practices are being adopted.

Each recommendation needs start conditions, exit conditions and expected artifacts.

9.4 RACI-style generation

SemanticFlow should generate a configurable responsibility matrix by asset type, domain, sensitivity, criticality, certification state and target.

Example activities:

- Define business meaning.
- Design semantic calculation.
- Validate source availability.
- Implement target expression.
- Classify sensitivity.
- Approve certification.
- Publish artifact.
- Accept risk.
- Audit evidence.

The matrix must be configurable and never hardcoded as universal truth.

9.5 Organizational safety

- Do not score individuals.
- Do not infer performance, competence, emotion or intent.
- Do not recommend termination, discipline or compensation decisions.
- Do not expose personal data by default.
- Frame recommendations around system, role and workflow gaps.
- Require human review for organizational changes.

- Impact analysis generated.
- Affected assets identified.
- Data Architect reviews architectural impact.
- Domain Owner reviews business impact.
- Engineering teams implement adaptations.
- Governance and quality gates run.
- Target artifacts compile.
- Platform publishes.
- Audit evidence records the decision.

10.3 Certification lifecycle

- DRAFT.
- SEMANTICALLY_VALID.
- TECHNICALLY_VALIDATED.
- GOVERNANCE_REVIEWED.
- DOMAIN_APPROVED.
- CERTIFIED.
- DEPRECATED.
- RETIRED.

Rules:

- State transitions must be configurable.
- Critical policies cannot be bypassed by lowering a score threshold.
- SemanticFlow initially generates workflow state and recommendations, not a full workflow server.

- Python 3.10 or later, aligned with current project support.
- Pydantic v2 contracts.
- Type annotations.
- Ruff formatting and linting.
- Deterministic output.
- Offline-first operation.
- No mandatory cloud SDK.
- Stable identifiers.
- Output path safety.
- Atomic output replacement when possible.
- Structured diagnostics.
- No secrets in outputs.
- Configurable organizational metadata handling.
- Performance suitable for large metadata graphs.
- Cycle-safe graph traversal.
- Backward-compatible migration.

17. DEFINITION OF DONE
======================================================================

A Lens is complete only when:

1. It implements the common contract.
2. Its purpose and decisions are documented.
3. Visible and hidden fields are tested.
4. It generates Markdown and JSON.
5. It has a dedicated fixture.
6. Unit tests pass.
7. Golden tests pass.
8. Cross-lens consistency passes.
9. No-mutation tests pass.
10. Recommendations include evidence.
11. Privacy behavior is tested.
12. Full regression passes.
13. The ThinkingSeed is updated with evidence.

The Leadership Cockpit is complete only when:

1. It resides in an isolated leadership package.
2. It consumes public framework contracts.
3. It does not duplicate core scoring or lineage logic.
4. Aggregates reconcile with detailed evidence.
5. Missing data is explicit.
6. No individual productivity scoring exists.
7. All modules have dedicated tests.
8. Outputs are deterministic.
9. CLI and SDK entry points are documented.
10. Full regression and architecture-boundary tests pass.

- Qlik emitter.
- A full HR system.

- Automated staffing decisions.

- Model training.
- Feature store behavior.
- Cloud tenant deployment.
- Financial value estimates without explicit source data.

Looker and Qlik remain future target adapters after the Canonical Model, Persona Framework, Capability Planner and Power BI adapter are fully hardened.
